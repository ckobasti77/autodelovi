## Skeptic analysis (no new measurements; data above re-read from the finder's and the perf verifier's JSON)
- Method: perf-3d-frames.mjs (line 32-36) and perf-3d-profile.mjs (line 26-30) launch ONE Chromium and open a new context per run,
  so only run 0 of each series is a first visit (cold GPU program cache). Runs 1-2 are warm.
- Desktop 1x: cold run 0 = 374 + 251 ms long tasks (TBT 525); warm runs 1-2 = 58 ms / none (TBT 8 / 0).
  => at 1x the whole start cost is first-use shader compilation; the canvas chunk evaluates in ~20 ms.
- PMREM GGX compile, cold, 1x: 336 / 344 / 457 ms (finder, 3 launches) and 350 ms (verifier) getProgramParameter self inside
  PMREMGenerator.fromEquirectangular -> _applyGGXFilter (three 0.186.1, GGX_SAMPLES = 256 constant loop). First frame after
  compileAsync: 138-191 ms getProgramParameter (programs not covered by compileAsync / linked at draw on ANGLE D3D11).
- Code: components/three/canvas/loadCar.ts:96-105 calls pmrem.fromEquirectangular(hdr) synchronously; nothing precompiles the
  PMREM materials through KHR_parallel_shader_compile. HeroCanvas.tsx:126 compileAsync covers only the scene materials.
- The 4x/6x "worst" ranges (291-616 ms in warm runs) are dominated by the canvas chunk evaluation (position ~3, 255-489 ms at
  4x/6x; 'H turbopack' self 127-277 ms) = the lazy 3D chunk inside the 3D-CONTRACT F7.3 budget (282 KB of 350 KB gzip).
  That is a separate, accepted cost, not this root cause.
- Mobile rows are a desktop RTX 4060 on ANGLE D3D11 (HLSL compile in the GPU process) with CDP CPU throttling of the renderer;
  no phone GPU backend (Android ANGLE-Vulkan/GLES, iOS Metal) was measured, so the phone magnitude is unverified.
- "Frame of 683 ms mid-scroll": rAF gap = main thread. The track is CSS sticky (3D-CONTRACT F9 / D104), intent listeners are
  passive (HeroStage.tsx:192-195), canvas has touch-action: pan-y -> the page keeps scrolling on the compositor; the scrubbed
  explode/poster, text reveal and taps stall. Cold run only (683); warm runs 333/300.
- Standards: BRIEF §9 TBT is the Lighthouse lab bar (D112 method); Lighthouse mobile never starts the 3D (touch devices have no
  idle start, HeroStage.tsx:196-202) and the desktop preset TBT is 0 -> no §9 bar missed. BRIEF §4 "never block the page" is
  spelled out as poster first / 3D after first paint, which holds. WEB-QA §4 "tasks <= 175 ms" was measured with SwiftShader,
  not a hardware GPU -> the doc claim does not hold for Windows Chrome/Edge (ANGLE D3D11) first visits and must be corrected.
- Not a localhost artefact: shader compile does not depend on the network; on a real network the same tasks run, only later.
Verdict: partially confirmed, P2 (one-time per cold GPU cache, Windows D3D11 verified, mobile unverified, no flow blocked).
